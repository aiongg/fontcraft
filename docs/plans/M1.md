# M1 plan: source model and file I/O

_Planning pass of 2026-10-07. Status: **accepted by the owner 2026-10-07**; one agent throughout. **Done 2026-10-08**: every package, M1.7 included (§ 4)._

M1 grows the M0 model into the full source model and adds reading and writing for every source
format, plus opening compiled fonts. Everything after it (compiler oracles, real test fonts, the
editor) depends on M1.

## 2. What the planning pass found

- **The corpus is fetched and the oracles are installed** on the build box: fontc 1.0.0 (cargo),
  fontmake 3.12.1 with glyphsLib and fontTools (uv). Corpus size 226 MB.
- **Corpus contents.** 232 `.glyphs` files (75 version 2, 157 version 3), 14 packages, 140 UFOs,
  1 UFOZ, 112 designspace files. 182 of the `.glyphs` files carry an `.appVersion`, meaning the
  reference app saved them at some point (fontc's test files may have been edited by hand since).
  At least 58 UFOs were written by fontTools ufoLib (paths with spaces were not counted).
- **There is no version 4 file in the corpus.** The owner has no licence, so we cannot make any.
  GlyphsSDK (Apache-2.0) publishes v2 and v3 samples and a v3 package, but no v4 sample. GitHub
  code search finds public v4 files (for example an Andika test fixture, a few OFL families and
  course material); each needs a licence check before it is pinned. Without v4 samples, the v4
  writer can be built from the schema but its byte fidelity cannot be measured.
- **GlyphsSDK's sample files belong in the corpus.** They exercise many documented keys on purpose.

Rules found on the way, for the `.glyphs` writer (M1.3):

- The trailing comma after the last element of a multi-line list is a version 4 rule; no
  unedited version 2 or 3 file has one.
- Every string containing `-` or `/` is quoted (10,711 cases, no exception). A bare string needs
  at least one letter or digit (`..` is quoted, `.notdef` is not).
- Version 2 writes code points as bare hexadecimal with leading zeros (`unicode = 0041;`); the
  property-list layer reads them as strings, and the `.glyphs` reader must interpret them.
- Number-like dictionary keys are bare in `Axis Mappings` and quoted in string-keyed settings
  (TrueType `deltaV`). The model writer needs a per-key choice, so `Str` needs a public way to ask
  for a bare spelling.

### M1.2 The model (serial: everything else depends on it)

**Progress (2026-10-07):** steps 1 and 2 done for the M0 fields: tagged `Extra` with property-list
values, `Arc` parts, the glyph table with its name index, metric definitions with per-master
values, layers with their own ids, transforms kept as written. Native format version 2 with an
upgrade from version 1. M0 debt fixed: name lookup, the top-level copy, the double parse, no-op
undo steps.

**Native format:** version 2, written with a diff-friendly layout (scalar-only objects and arrays
on one line, whole numbers without a decimal point, sorted keys; Oswald 4.4 MB against 8.2 MB
before), optionally gzip-compressed with the state kept on saving. Every reference-written
`.glyphs` source survives `.glyphs` → `.fontcraft` → `.glyphs` byte for byte
(`roundtrip.nativeLosslessFromGlyphs`, corpus test).

**`crates/io-glyphs`, first cut:** versions 3 and 4, single files. Typed: family name (v4 from
its `familyNames` property), units per em, version, metric definitions and values, masters, glyphs
(name, code points, export), layers (id, master, width), paths, nodes, components, anchors;
everything else in `Extra`. Shapes the model cannot hold are kept as raw shapes.

### M1.4 UFO and designspace (`crates/io-ufo`)

Our own reader and writer (question 11), on the `plist` crate's XML half:

- A designspace and its UFOs merge into one document; saving splits it back into the same files
  (`roundtrip.ufoMastersShareStructure`, `roundtrip.designspaceVerbatim`).
- GLIF file names, layer directory names, identifiers, libs and `data/` kept verbatim.
- UFO 2 read and (per question 12) written; UFOZ read.
- Glyphs-only data carried in lib keys spelled as glyphsLib spells them (question 7).
- **Gate measures:** byte-identical round trip of the ufoLib-written UFOs and of the designspace
  files; norad reads our output; a `.glyphs` → UFO → `.glyphs` trip loses only what the loss
  report lists.

**Done (2026-10-08).** `crates/plist` gained a lossless XML tree and XML property lists;
`crates/io-ufo` reads and writes GLIF, UFO 2 and 3, and designspace documents, and reads UFOZ.

How fidelity works. The writers produce fontTools' layout (glifLib, plistlib, designspaceLib;
MIT, credited in `NOTICE`). The readers keep only what those writers would spell differently:
a file's layout (declaration, document type, indentation unit and level, final line break,
whole numbers as floats), and a start tag or scalar whose text is not the writer's. A kept
spelling is used only while it still means what the model holds, so an edit writes the
canonical form. Each UFO property list is kept as read and patched with what the model changed.
A designspace document is kept as an XML tree and patched where axes, sources or instances
changed. In a designspace, values a master's UFO held differently from the default source's
(code points, file names, feature code, export lists, groups, font info) stay with that master
while the model leaves the default master's unchanged.

### M1.7 The typed model (added 2026-10-08)

The owner chose to finish the model before M2 (question 1 of the M1.4 results) and to carry
Glyphs-only data into UFO lib keys now (question 2). A census of the corpus
(`crates/engine/tests/engine/extra_census.rs`, ignored test) lists what still travels in `Extra`:
custom parameters, properties and settings; instance details; stems, numbers and master guides;
glyph metadata and metrics keys; layer attributes, names, backgrounds, guides, hints,
annotations and images; node, path and component attributes; and on the UFO side every
`fontinfo.plist` key beyond the basic ones, libs and groups.

**Goal.** Every documented field is a model field, so commands, the compiler and the other
format can use it. What no document explains (version 4 `group`, `hoi`, `kerningContext` keys,
`settings.dependencies`) is held in a typed container with its stored value, so it can be
listed, copied and written back but not interpreted.

**One vocabulary for both families.** Equivalent data meets in one field, chosen as follows.

| Kind of data | Model home | Mapping |
|---|---|---|
| Names (family, designer, copyright, licence, sample text…) | `properties`, with the reference's property keys, localised | UFO `fontinfo.plist` keys and designspace localised names map to property keys |
| OS/2, hhea, vhea, post, head, gasp and similar values | ordered `params` (name, value, disabled) on font, master or instance, under the reference's parameter names | UFO keys with an equivalent use the reference's name; UFO-only keys keep their UFO name |
| Per-master UFO font info that differs between masters | the master's `params` | as now: written back to that master's UFO |
| User data and libs | `UserData`, an ordered dictionary that remembers its syntax | values move to the other syntax without their spellings |
| Glyph metadata (category, production name, colour label…) | glyph fields | UFO public lib keys (`public.openTypeCategories`, `public.postscriptNames`, `public.markColor`…) |
| Glyphs-only data in a UFO | the same model fields | glyphsLib's `com.schriftgestaltung.*` lib keys, read and written |

The crosswalk is ported from glyphsLib (Apache-2.0, credited in `NOTICE`), so a UFO we write
reads in fontmake as one glyphsLib would have made.

**Steps.** Each step types a group of fields in the model, in `.glyphs` versions 2 to 4, in UFO
and designspace, and in the native format, and must leave every corpus round trip identical.

1. Vocabulary: `Param`/`Params`, `Property`, `UserData` with its syntax, colours.
2. Font: properties, parameters, settings, date, app version, user data; the version 2
   top-level names. UFO font info through the crosswalk.
3. Axes (default, range, map, names, labels), masters (stems, numbers, guides, icon,
   visibility, properties, parameters, user data; version 2 weight, width and custom values),
   instances (id, kind, manual interpolation, visibility, classes, style linking, properties,
   parameters, user data, file name). The designspace document's axes and instances become
   these fields; the kept document tree stays for byte fidelity.
4. Glyphs: production name, classification, case, direction, metrics keys, colour, tags, note,
   lock, last change, sort names, smart-glyph settings, user data.
5. Layers: name, attributes (intermediate coordinates, alternate rules, colour layers, smart
   poles), vertical metrics, background, guides, hints (as stored node references, interpreted
   in M10), annotations, image, metrics keys, colour, visibility, user data. UFO
   `public.background` becomes the master layer's background; other UFO layers become backup
   layers.
6. Shapes: path lock and drawing attributes; node join (smooth, tangent), flags, name,
   identifier and user data (rare data behind one pointer, so a node stays 32 bytes); component
   alignment, anchor, smart values, source master, lock, orientation, flags, identifier, user
   data; anchor lock, orientation, colour, identifier; version 4 image shapes. Shape groups stay
   stored values.
7. Kerning context (version 4) as stored values; UFO groups that are not kerning groups as
   `groups`; feature labels and the snippet markers converters write in `features.fea`.
8. glyphsLib lib keys: Glyphs-only data written into UFOs and read back (8a: the font, masters
   and instances; 8b: glyphs, layers and shapes).

**Done (2026-10-08).** Every documented field of `.glyphs` versions 2 to 4, UFO 2 and 3 and
designspace documents is a model field, in the native file too, and Glyphs-only data travels in
glyphsLib's UFO lib keys. What no format document explains, and values the plan keeps as stored
(gradients, shadows, shape groups), stay in `Extra` with their spelling. The four measures are
met, with the exceptions the table names.

Fixes the measures led to:

- A component or background image whose matrix has a shear (a slanted component in a UFO) could
  not be saved as `.glyphs` versions 3 and 4. The decomposition now finds the slant, as
  glyphsLib 6.15 does (`decomposeGlyphs3Transform`), and takes the arithmetic noise off the
  numbers.
- Version 2: the properties version 2 keeps in parameters (`vendorID`, `license`,
  `licenseURL`, `versionString`, `uniqueID`, `trademark`, `description`, `sampleText`) and the
  instance names it keeps in parameters (`familyName`, `postscriptFontName`…) are written as
  those parameters; `Color Palettes` colours are written as `"r,g,b,a"` strings; an axis range

- Loss reports. New lines: glyphs without layers; parameters under a UFO name that come back

#### Steps 1 and 2: the vocabulary and the font information

Step 1: `Param`/`Params`, `Property`/`Properties` (plain or localised), `UserData`
(`crates/model/src/info.rs`); in the native file a value that holds a boolean or a date is
stored as XML text. Step 2:

- `.glyphs`: the font's properties, parameters, settings, date and user data, `.appVersion`, and
  version 2's top-level names and settings; masters' icon, visibility, properties, parameters
  and user data; instances' properties, parameters and user data (`crates/io-glyphs/src/info.rs`).
  A value is typed only when the writer would spell it the same way, so hand-edited files keep
  their spellings.
- UFO (`crates/io-ufo/src/fontinfo.rs`, the crosswalk in `docs/spec/31-glyphslib-crosswalk.md`):
  every `fontinfo.plist` key except the ones step 3 types (blue zones, stems, guidelines) is a
  property, a parameter under the reference's name, or a parameter under its UFO name; the
  creation date is the font's date; `lib.plist` is the master's user data. In a designspace the
  default source's font information is the font's, and another master keeps only what differs.
  A key whose model form would not write back to the same value is kept as written (4 in the
  corpus: negative `winDescent` values).

Differences from glyphsLib, on purpose:

| glyphsLib | FontCraft | Why |
|---|---|---|
| font information goes on the font and again on every master | on the font, and on a master only where its UFO differs | one value, one place |
| a switched-off parameter is written like any other | not written; the loss report lists it | it is not used |
| a UFO without `fsType` or underline values reads as no parameter | reads as ufo2ft's default (`fsType` bit 2, 5% and -7.5% of the em), since the model means the reference's defaults | a UFO keeps compiling the same after conversion |
| name records come back as `Name Table Entry` parameters | records for a property's languages come back as that property's localised values | no loss for localised names |
| version 2 without an `Axes` parameter: always three axes (Weight, Width, Custom) | as many default axes as the highest axis key any master or instance uses (up to six); none when no key is used | a font has only the axes it uses |
| version 2 instance written with both `active` and `exports` | `exports = 0`, as the format document has it; a file's own `active` or `exports` key is kept | the format document names `exports` |
| version 2 master name: the `Master Name` parameter wins over the `name` key | the `name` key wins; the parameter and the name parts give the name only when the key is absent | the key is what the file says |

#### Step 3b: UFO zones, stems and guidelines (`crates/io-ufo/src/design.rs`, ported from glyphsLib's builder)

|---|---|---|
| `postscriptBlueValues`, `postscriptOtherBlues` | metric overshoots, `Master::zones` | pairs become zones by spec 31 § 4.1; a zone at the position of a metric the file has becomes that metric's overshoot (the first one without one); a zone of size 0 and the rest stay zones. - A key is typed only when writing it gives the same value; otherwise it stays as written, as a

  different numbers of stems (fontTools' `BuildAvar*` test files). Every guideline list is typed.

  italic angle's overshoot (Oswald has one), guide filters, angle locks, measurements and label

- Checked against glyphsLib's output for `GlyphsFileFormatv3.glyphs`, `LinkedFontv3.glyphs` and

Differences from glyphsLib, on purpose:

| glyphsLib | FontCraft | Why |
|---|---|---|
| a UFO guideline with only `y` 0 reads as a vertical line at x 0 | a horizontal line at y 0 | the UFO specification says so; glyphsLib writes a horizontal guide through the origin that way |
| a UFO guideline's colour and identifier are added to the guide's name | fields of the guide; added to the name only when writing `.glyphs` | the name stays the name |
| blue values and stem snaps are taken as they are | a pair glyphsLib would reorder, or stems a master cannot share with the others, stay as written | byte fidelity |

Decisions:

- **Smart components** stay components; their values go to `componentsSmartComponentValues`, and
  the smart glyph's properties to `smartComponentAxes`, so both come back (glyphsLib's own
  reader takes them). A UFO compiler sees a component of the smart glyph's master layer, not the
  interpolated outline glyphsLib draws.
- **Anchor user data** goes to `public.objectLibs` under the anchor's identifier. An anchor
  without one gets an identifier derived from the glyph's name and the anchor's name and position
  in the layer (a 128-bit FNV-1a hash written as a UUID), so saving twice writes the same file.
  Reading takes a derived identifier off again; any other identifier (glyphsLib's random ones)
  stays the anchor's. Entries for other objects stay the layer's user data.

Differences from glyphsLib, on purpose:

| glyphsLib | FontCraft | Why |
|---|---|---|
| `lastChange` only with `minimize_glyphs_diffs` | always (unless `Disable Last Change`) | the date comes back |
| layer ids and order keys only with `minimize_glyphs_diffs`, for every layer | written where they are needed: ids when a UFO layer's layers share one, order keys for glyphs whose order the reader would not give back | the layers come back in their order, without a key per layer of every glyph |
| a non-exported glyph gets `Glyphs.Export = false` in each GLIF | `public.skipExportGlyphs`, as before; a file's own key is read and kept | one list for compilers (fontmake's choice) |
| non-spacing marks are found through its glyph database | only glyphs whose own category says so (8 glyphs of Oswald keep their width) | there is no glyph database yet (M4) |
| node user data of an open path's first node is not written | written | it comes back |
| an anchor with user data gets a random identifier; `public.objectLibs` is not read back | a derived identifier; read back | the same file on every save; the data comes back |
| a smart component is drawn as outlines | a component with its values | as above |
| layer user data under reserved prefixes are not written; layer libs of layers a UFO lacks are dropped | written to `lib.plist` | they come back |

#### Step 8c: intermediate and alternate layers in a designspace (`crates/io-ufo/src/designspace/sparse.rs`, `rules.rs`, ported from glyphsLib's `builder/sources.py`, `builder/bracket_layers.py` and `builder/transformations/align_alternate_layers.py`, and from fontTools' `varLib/featureVars.py`)

| Model | Designspace and UFOs | Rule |
|---|---|---|
| intermediate layer (`attrs.coordinates`) | its UFO layer `{c1, c2}` (step 5b), and a sparse source `<source filename name="<master id> {c1, c2}" layer="{c1, c2}">` | one source per UFO layer name and master, after the master's source, sorted by location; an axis the coordinates leave out (or `-`) takes the master's value |
| alternate layer (`attrs.axis_rules`) | a glyph `<glyph>.BRACKET.varAlt<nn>` in every master's UFO; GLIF lib `com.schriftgestaltung.Glyphs._originalLayerName` = the layer's name | numbered per glyph by the first appearance of its region (an open end is the axis's end in design coordinates); a master without an alternate layer for the region gets a copy of its master layer, named `""` |
| | `<rules>`: rules named `BRACKET.<axis>_<min>_<max>`, one condition set each, for exported glyphs only | one rule per alternate layer, overlaid by fontTools' `overlayFeatureVariations`; `Feature for Feature Variations` `rclt` gives `processing="last"`, another tag (not `rvrn`) the document lib key `com.github.fonttools.varLib.featureVarsFeatureTag` |
| | the bracket glyph's components, kerning, groups, production name, `GDEF` class | a component goes to its glyph's bracket glyph of the same region; the bracket glyph joins its glyph's kerning groups and pairs; the production name gets the suffix; a font that states `GDEF` classes gets one by glyphsLib's anchor rule; `public.glyphOrder` leaves bracket glyphs out |
| composites | copies of their master layers for the regions of their components' alternate layers (glyphsLib's `align_alternate_layers`), written as master-layer copies (`""`) | |
| an alternate layer's background | the UFO layer `<layer name>.background`, under the bracket glyph's name | as glyphsLib's `to_ufo_glyph_background` |

Reading. The designspace reader converts what is in glyphsLib's form and keeps the conversion only
when writing it gives back the files as read, or the files the plain reading writes. Otherwise
the earlier reading stays: a master per sparse source, bracket glyphs as glyphs, rules as written.

- A sparse source in glyphsLib's form is a `layer` of a UFO another source holds, named
  `<that source's name> <layer>`, whose layer name `{…}` states the source's location (fewer
  coordinates: the other axes at the master's location; more: the extra ones ignored). Its glyph
  layers get the coordinates; no master is made.
- Rules in glyphsLib's form are all named `BRACKET.…`, with one condition set of conditions on
  axes with both ends, substituting `<glyph>` with `<glyph>.BRACKET.<suffix>`. Each master layer
  of a bracket glyph with a non-empty `_originalLayerName` becomes an alternate layer of that
  name; the copies go; components point back; `<name>.background` becomes its background; the
  bracket glyph's kerning and group membership go with it.
- A bracket glyph's rules name it only where no later bracket glyph of its glyph takes over. The
  reader takes the box around those regions and runs each end on to the axis's end as far as that
  stays clear of the regions where the rules give the glyph no bracket glyph or an earlier one
  (checked at the middle of each cell between the rules' bounds). So `[300]` and `[600]` come
  back as written. A range that really ended where a later layer starts comes back open.
- Every corpus designspace still writes back unchanged. The three glyphsLib-made fontc documents
  with sparse sources (`IntermediateLayer`, `wght_var`, `MultiModelIndirect`) now read as
  intermediate layers; the other documents with rules or sparse sources (fontTools' and fontc's
  hand-made ones) keep their reading. Census: designspace layer masters from 7 in 5 sources to 1
  in 1.
- A single UFO does what glyphsLib's `to_ufos` does: intermediate layers are UFO layers without a
  location, alternate layers are left out; both are reported.

Loss reports. Saving as a designspace no longer lists alternate layers or the intermediate
layers' coordinates (`ufo::layers_left_out`, `layer_losses` and `shape_losses` take the target).
New lines: alternate layers of glyphs that are not exported (they come back as glyphs of their
own); ranges that a later alternate layer of the glyph overlaps and that come back running on to
the axis's end; alternate layers that later ones cover entirely (the whole document then reads
back as written); glyphs whose alternate layers come back after their other layers;
intermediate coordinates that take the master's value. Alternate layers' ids are reported, as
for other layers.

Checked against glyphsLib (`to_designspace`, default mode) on the 21 corpus sources with
intermediate or alternate layers that glyphsLib converts (fontc's test files and the format 3
sample): the same rules (names, conditions, substitution order, processing, feature tag) and the
same sparse sources (layer names, locations, order) in all of them; the bracket glyphs have the
same names, widths, outlines, components, `_originalLayerName` values, kerning pairs, group
members and skip lists, except anchors glyphsLib propagates to composites (6 sources), production
names and `GDEF` classes from glyphsLib's glyph database, and version 2 layers without a width
(glyphsLib makes them 600 wide). `glyphs2/AxisRules.glyphs` has other axes (an earlier
difference). glyphsLib's `to_glyphs` reads our designspaces back with the alternate layers under
their names and the intermediate layers as `{…}` layers. fontmake builds variable fonts from four
of them, with feature variations in `rvrn` or `rclt`. Our reader converts glyphsLib's designspaces
of 14 of these sources and ours of 17. The others keep the plain reading: alternate layers that
later ones cover entirely (3 sources, both writers), glyphsLib's propagated anchors in the copies
(2), an alternate layer glyphsLib writes without a name (1), and a glyph with an alternate layer
but no master layer, which neither writer writes (`glyphs2/AxisRules.glyphs`).
`crates/engine/tests/engine/cross_format.rs` compares the alternate layers (by master and name, region,
drawing and the rest) and the intermediate layers' coordinates in the `.glyphs` → designspace
trip, and a new test does so for every corpus source with such layers.

Differences from glyphsLib, on purpose:

| glyphsLib | FontCraft | Why |
|---|---|---|
| the copies `align_alternate_layers` adds are named after the master layer and the rule in format version 2 (`Regular [150]`), so `to_glyphs` makes them layers | named `""` in every version, as master-layer copies | they come back as nothing, as in the source |
| an alternate layer without a name is written with `""` and does not come back | written with a name from its rules (`[300]`, `]600]`, else `[]`); the name is reported | the layer comes back |
| `to_glyphs` gives alternate and intermediate layers names only; format 3 attributes are lost | rules and coordinates read back from the designspace | the model comes back |
| a sparse source is named `<family> <style> <layer>` | `<master id> <layer>` | a master's source carries its id (step 3c) |

### 8.1 `openstep-plist` 1.1.0 and `glyphslib` 0.2.8 on `.glyphs` files

Each file was parsed and written back, then compared with the original byte for byte.

| Tool | Files | Identical | Different | Failed to read |
|---|---:|---:|---:|---:|
| `openstep-plist` (generic value, no model) | 245 | 0 | 245 | 0 |
| `glyphslib` (typed model) | 245 | 0 | 218 | 27, including all 5 version 4 files |

- The value type cannot keep spellings: dictionaries are `BTreeMap`s (sorted, so source order is
  lost where it is not alphabetical), numbers are `i64` or `f64` (so `1.0` and `1` collapse), and
  strings do not record whether they were quoted.
- The writer has one layout. The first difference in most files is an array the app writes over
  several lines and the crate writes on one, or the trailing comma version 4 puts after the last
  element of a multi-line list.
- The parser indexes and unwraps freely, so hostile input can panic it; our rules would require
  a guard around every call.

**Decision:** our own `plist` crate (M1.1). `glyphslib` and fontc's `glyphs-reader` stay as second
readers in tests (versions 2 and 3).

### 8.2 norad 0.19.0 on UFO and designspace

### M1.20 Open and save reports (writer; built)

A save that cannot hold part of the document, the members of a font collection and what an open left
out reach the person instead of staying in a command's reply.

- **Loss question.** `file.lossReport` (query) gives a save's or UFO export's losses without
  writing, with the glyphs of each kind, what a UFO keeps only in private lib keys, and `fresh`: what
  the document's file does not already leave out. A person's Save, Save As or Export UFO with a
  non-empty `fresh` asks first (Save Anyway, Cancel, smart components as outlines for a UFO). Save
  from the close question asks too, and the close waits for the answer. `strict` is the explicit
  answer: `false` writes, `true` refuses and writes nothing. Control-channel and CLI runs never ask.
- **Collections.** A person's File › Open… of a collection of several fonts lists them; each chosen
  member opens as its own document. A collection of one font opens without `face`.
- **View-only mark.** "View Only" after the title and a bar over the document with Save As…, until it
  is saved. `DocState::file_format` is the format Save writes: a font saved as `.fontcraft` keeps
  where it came from (`source.format`), but Save writes the native file, and the document is not
  view-only, not realigned and not renamed when it opens again.
- **Open warnings.** Whatever `warnings` a `file.open` returns are kept per document, counted in the
  bar and listed by `file.openReport`.
- `window.fileQuestion` answers either question; `ui.inspect` has `fileQuestion` and `openReport`.
