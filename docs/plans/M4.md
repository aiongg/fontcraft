# M4 plan: Font View and glyph management

_Planning pass of 2026-10-10. Status: **done** on 2026-10-10 (M4.12): every § 5 measure is met (§ 5 › Results). § 7 questions 1 to 8 are answered, question 9 stays open._

M4 turns Font View from a plain glyph grid into the place where a font's glyph set is managed. It
adds the glyph database (names, Unicode values, categories, scripts, production names), the glyph
properties and the commands that set them, adding, duplicating, renaming and removing glyphs,
copying glyphs between fonts, List View, the inspector, the sidebar with its categories, languages
and filters, search, the Glyph Info and Selection Info windows, and the Start Window. The glyph
database also closes two compiler gaps left from M2: production names in exported fonts and the
zero advance of non-spacing marks that only the database knows.

## 1. Scope

and 1 setting. Six commands are live today (`fontView.show`, `fontView.setSelection`,
`view.editSelectedGlyphs`, `glyph.newGlyph`, `glyph.removeGlyph`, `glyph.setUnicodes`). The pass
moved 19 rows into M4 (§ 2) and keeps every row; five parts of rows wait for later milestones.

  category, subcategory, script, case, direction, OpenType category, metrics keys, colour, tags,

  `disablesNiceNames` and `keepAlternatesTogether`. M4 needs no new stored field. It needs derived

## 3. Answers and decisions

### The glyph database: where its data comes from

| Source | Licence | Gives | Use |
|---|---|---|---|
| GlyphsInfo `GlyphData.xml`, `GlyphData_Ideographs.xml` (github.com/schriftgestalt/GlyphsInfo) | MIT up to 2024-11-22 (commit 9e03a49), BSD-3-Clause after, copyright Georg Seifert; README carries Adobe's BSD-3-Clause AGL notice | about 34,000 records with nice name, code point, legacy code point, category, subcategory, case, direction, script, description, production name, alternative names; about 40,000 Han records | **Recommended main source.** The only open data with the reference's nice names, categories and production names. glyphsLib and fontc ship the same file, so FontCraft and both oracles agree by construction |
| Adobe Glyph List and AGLFN (github.com/adobe-type-tools/agl-aglfn) | BSD-3-Clause | legacy name → code points; the recommended name subset | Name parsing (`export.aglNameParsing`), the category fallback, and whether a nice name may be exported as is |
| Unicode Character Database (unicode.org/ucd) | Unicode License v3 (OSI-approved, MIT-like; keep the notice) | General_Category, Script, Bidi_Class, names, decompositions | Category fallback for unknown names, directions per script, assigned code points for ranges; decompositions later for M6 |
| fontc `glyphs-reader` (crates.io 1.0.0) | MIT OR Apache-2.0; its data is the GlyphsInfo file again: `resources/*.dat` were generated from glyphsLib 6.13.1, whose two XML files equal 6.15.0's (its `data/VERSION`, which names 6.6.6, covers only the test file there) | category, subcategory, production name, script, code point | **Oracle, not a source**: the cross-check of § 5 compares with it. Its tables lack case, direction, alternative names and descriptions |
| glyphsLib `glyphsLib/data/` | the data file's licence is GlyphsInfo's (above); glyphsLib is Apache-2.0 | the same XML | Oracle for fontmake's names; the pinned GlyphsInfo commit is the one whose files equal glyphsLib 6.15.0's copy, so the fontmake oracle agrees. That is commit 1f126bd of 2026-04-28 (both XML files match by git blob hash), whose LICENSE is BSD-3-Clause; glyphsLib's `GlyphData_LICENSE` still carries the older MIT text |

How the data enters FontCraft: `cargo xtask glyphdata` fetches the three sources at pinned commits
(listed in `xtask/glyphdata.toml`, as the corpus pins its sources), writes compact generated tables
into `crates/glyphdata/data/`, and commits them with an `ASSETS.md` row each and `NOTICE` entries
(GlyphsInfo's licence at the pinned commit, the AGL BSD-3-Clause notice, the Unicode licence). The synthesis rules are ported
from fontc's `glyphs-reader/src/glyphdata.rs` (Apache-2.0) with a file-header credit. Nothing comes
from inside an app: the reference's larger built-in data (with sort names, anchors and
compositions) is never used.

Alternatives for the owner (§ 7, question 2): build the database from the UCD and AGLFN alone,
with names from LettError's glyphNameFormatter (BSD-3-Clause); or take fontc's generated tables.
The first gives names and categories that differ from every `.glyphs` file and from both oracles;
the second lacks four fields M4 shows.

### Design decisions (new questions of this pass)

| Question | Answer for M4 |
|---|---|
| Where is a glyph's effective property computed? | One function in `model` (`glyph_props.rs`) takes a glyph and the session's `GlyphData` and returns every database-backed property with its source: `stored`, `custom`, `database`, `synthesised` or `none`. Font View, `glyph.getInfo`, smart filters and the compiler all use it. Results are cached per document revision |
| Is Unicode a stored or a derived property? | Stored, as both source formats store it. It is set from the database when a glyph is created and when its base name changes to a name the database gives code points (`glyph.rename` guesses) |
| Custom glyph data | Built-in data, then per-user files (`GlyphData*.xml` in FontCraft's settings folder `Info/`), then the file beside the source or in its `Info/` folder unless *Ignore custom GlyphData file* is set; later layers win per record. A malformed file is ignored and reported. The engine holds the merged data per document |
| Where do filters, the visible scripts, recent documents and the chooser's last picks live? | In the user settings, as in the reference (tutorial: filters are "available in all Glyphs files"), § 7 question 4. The engine holds a `Settings` store; `settings.get` and `settings.set` read and write it; the desktop app saves it as JSON in its settings folder, the browser through eframe's storage |
| Kind of the filter commands | `engine`: `fontView.addSmartFilter`, `addListFilter`, `addFilterFolder`, `editFilter`, `renameFilter`, `removeFilter`, `moveFilter`, `setVisibleScripts` change the settings store, which the engine holds, so the CLI, MCP and `fontView.queryGlyphs` reach the same filters. They make no undo step |
| How is a smart filter stored? | As a rule tree, `{all \| any \| none: [rule…]}` with `rule = {property, op, value}`, which compiles to the glyph predicate language of `12-feature-code.md` § Glyph predicate tokens. The Custom rule takes predicate text in that language. One evaluator in the new crate `glyphquery` serves smart filters, the Custom rule, global-guide filters and, in M8, the feature-code tokens |
| Glyph order | `fontcraft_model::glyph_order(font)`: the names in the `glyphOrder` parameter that exist (section-header lines `**Title**` skipped), then the remaining glyphs in stored order. Font View and export both use it. An opened file is never re-sorted; a glyph added, renamed or given a sort name is placed by the sort key (`glyphOrder.default` guesses). § 7 question 5 |
| Invalid glyph names at export | `file.exportStatic` and `file.exportAll` refuse a font with an invalid name and name the glyph and the position (handbook). `font.compile` and the CLI follow fontc: sanitise and warn (`compile.productionNameSanitising`). § 7 question 8 |
| Font View's master | `view.selectMaster` with Font View showing sets Font View's master (Cmd+1 to Cmd+9). Cells, the layer colour, the layer rules of smart filters and *Content of Active Layer* use it |
| Last Changed | `Session::edit` stamps the glyphs an edit changes, unless the font's *Write lastChange* parameter is off. The time comes from a clock the app gives the engine; tests use a fixed clock, so results stay reproducible |
| Selection in Font View | Stays in `UiState` (`selected_glyphs`), in selection order. Batch commands get `glyphs` from it through the `targets` mechanism of M3 |
| Regular expressions | The `regex` crate (MIT OR Apache-2.0) with its size limits; `\N` in replacements becomes `${N}` (`regex.engine`) |
| Copying whole glyphs | `edit.copy {glyphs}` returns a `glyphs` JSON flavour (whole glyphs with all layers and properties) next to the M3 shape flavour; `edit.paste` with it adds glyphs (`.001` on a clash, components re-linked by name) |

### M4.1 Glyph database

Rows: the `glyphData.*` rows, `glyphName.*`, `export.aglNameParsing`, `export.productionName*`,
`glyph.productionNameDefault`, `glyph.niceNameVersusProductionName`, the `Ignore custom GlyphData
file` parameter.

1. `cargo xtask glyphdata --fetch` downloads the pinned sources into the git-ignored `corpus/`
   area; `--generate` writes the compact tables; `--check` runs the cross-check.
2. Crate `glyphdata` (L0, no workspace dependency):

   | Piece | What it does |
   |---|---|
   | Tables | records with every XML attribute, the Han file, AGL and AGLFN, general categories, scripts and bidi classes by code point range; indexes by name, production name, alternative name, code point. A versioned binary blob read with bounds checks, parsed once |
   | Lookup | `record(name)`, `by_code_point(cp)`, lookup order of § 4.2 of the note, alternative names last |
   | Synthesis | suffix split, ligature rules with the script suffix distributed, AGL fallback by general category, `_` names without category; ported from fontc with credit |
   | Production names | § 4.4 of the note, with the code-point name form |
   | Names | `nice_name(cp)`, `canonical_name(name)` (legacy, production and alternative names → nice name), `validate(name)` with the offending position |
   | Direction | stored value, else the record's, else RTL for scripts Unicode writes right to left |
   | Sort key | § 3 Glyph order; custom `sortName` and `sortNameKeep` when given |
   | Custom files | a reader for the flat `GlyphData.xml` form (document type declaration skipped, no entity declarations) with limits: 16 MB per file, 200,000 records, 1,024 bytes per attribute, depth 2 |
   | Search | substring match on name, description and hex code point; equality on the character; sort by any field; a result limit |

Tests: lookups and synthesis for every example in the rows (`A-cy.sc` → `uni0410.sc`,
`lam_alef-ar` → `uni06440627`, `uni00E4` → `adieresis`, `A.001` inherits from `A`, `A001` does
not); hostile custom XML; every public function on empty and huge input.

Done when: the § 5 cross-check measures are met, the crate builds for wasm, and the blob's size is
